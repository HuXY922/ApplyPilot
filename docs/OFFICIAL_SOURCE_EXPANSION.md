# Official-source expansion and hosted verification

Updated 2026-10-10 UTC. The final bounded-budget code is deployed, but **CXMT remains experimental: hosted browser acceptance is blocked by upstream network timeouts**. The final formal query still failed at category bootstrap. No more tuning or repeated source requests were performed after that result. Code/test/deployment success must not be presented as completed source usability.

## Delivered scope

- Preserve Python WSGI, SQLite schema, original ByteDance provider, model consent, CSRF/session boundaries, search/model quotas and manual tracker history.
- Implement one additional China official-source provider: CXMT / 长鑫存储. It is experimental and its hosted acceptance remains blocked. Default source configuration is `bytedance,cxmt`; existing deployments must explicitly update their environment setting.
- Fixed reviewed registry entries and public read-only endpoints. No arbitrary domains/URLs from HTTP clients, no added dependency, no CareerSail execution, no private application-submission API, no new credential or paid service.
- Send explicit job keywords and chosen recruitment category upstream for CXMT. Filter city locally. Do not automatically read or send applicant profiles or resumes to recruitment sources. Explicit keywords are sent upstream: users must not enter personal information, contact details or credentials. Common patterns are blocked, but detection is not a complete guarantee.
- Use a global 6 requests / 45-second discovery budget, fairly apportioned across remaining sources with a 30-second hard cap per source. Per-request wall-clock limits are 12 seconds for fixed host cxmt.zhiye.com, 7 seconds for ByteDance and 12 seconds for optional Ashby; no automatic retries. The single fetch slot and worker resource limits are unchanged. The default two-source run permits three ByteDance details and one CXMT bootstrap plus up to two list pages of 10 (at most 20 records). Network latency or source refusal can shorten coverage and is reported.
- Each CXMT result requires stable GUID, concrete complete JD fields, official category and current listing-state evidence. Status 1 is open; 2 is closed; other states remain unknown. Missing cohort remains unknown. Official complete-JD-list verification is explicitly different from individual detail-page visits.
- Record source identity, coverage, requests attempted, current verified and returned counts, pages, upstream total and stopping reason. No placeholder results, silent overseas fallback, or absence-based mass closure.
- 401/403 pause the source in the current process for operator review. 429 observes the full Retry-After (60 seconds if absent). State is shared by the current single worker's threads but is not persisted across service restart; do not restart to bypass it. There is no scheduled crawler.

## Automated verification

The final bounded-budget candidate passed 139 legacy tests, 214 ApplyPilot tests, 152 DOM checks / 95 real WSGI+SQLite requests, Python compilation, JavaScript syntax and genuine loopback HTTP/SQLite smoke. Independent review reproduced the two Python suites and DOM results. DOM rendering and source/model responses are simulated in that suite; real browser/source tests are recorded separately.

The tests cover dynamic category identity, the ten-record response limit, two distinct pages and deduplication, total counts versus bounded coverage, explicit keyword transmission and contact/credential rejection, TLS/public-DNS/destination/redirect guards, 401/403 pause and full 429 Retry-After, failure preservation of manual history, and clearing only obsolete search-error notifications.

The hard-deadline worker adds real offline process-lifecycle tests: blocked DNS/connect/headers/body are bounded, timed-out children are killed and reaped, one fetch slot recovers, output is bounded, and provider secrets are not inherited. A separate hosted offline check passed all six worker/IPC/resource/concurrency/recovery cases under the same app-user and service sandbox restrictions, with no official-source requests.

## Actual hosted observations

- Initial expansion deployment at 10:10:48 UTC passed server suites of 139 + 191 tests. An isolated app-user CXMT smoke read two pages of 20, yielding 40 distinct verified records from 45 upstream matches, without failures. This standalone check did not establish the browser route or each request's wall-clock duration.
- The first formal two-source browser run lasted 43.189 seconds and failed both sources. The old socket timeout did not bound all DNS/connection/response phases. No fake jobs were substituted and the prior seven records were retained.
- A fixed, isolated worker with parent-enforced deadlines was deployed at 10:35:05 UTC. Server suites passed 139 tests in 5.668 seconds and 206 tests in 9.059 seconds. The next formal run completed in 16.229 seconds, within the 30-second global budget, but still returned source timeouts. Deadline correctness and source availability are separate results.
- A strictly bounded two-request CXMT phase diagnostic succeeded in 8.031 seconds: bootstrap 2.026 seconds, first-page POST 5.553 seconds, 20 valid listing records. The POST body, URL, method and headers matched the formal request. The probe retained seven-second socket waits and a 30-second outer bound; unlike the app, it did not impose a separate seven-second wall limit on each request. Its valid-record count also precedes the app's local matching filter.
- A subsequent formal browser run took 23.852 seconds and was partial: ByteDance verified two records and returned one existing matching record without duplication; CXMT still timed out before completing a page. The manual tracker state was preserved. No particular network phase was proven to be the sole cause of the intermittent failures.
- To reduce response size rather than increase timeouts, the follow-up lowers the page size to 10 while retaining two pages, six total requests, the 30-second global budget and seven-second per-request deadline. It also clears an obsolete search-error toast on a newer query while retaining current source failures. The follow-up was deployed at 11:03:11 UTC; server tests passed 139 legacy tests in 5.711 seconds and 208 ApplyPilot tests in 9.089 seconds, ten changed file hashes matched, and HTTPS health passed. The reverse proxy and existing unrelated service remained running. The corresponding formal browser run lasted 20.614 seconds and remained partial: ByteDance returned one existing record, while CXMT timed out on its first category-bootstrap request. PageSize=10 and obsolete-toast cleanup were verified, but reducing the response size did not establish source availability.
- The last bounded adjustment keeps the smaller page size and raises only CXMT’s request cap to 12 seconds, with a 45-second global deadline and 30-second per-source cap under fair allocation. ByteDance stays at seven seconds; optional Ashby stays at twelve. The existing one-slot/resource/TLS/privacy restrictions, six-request limit and no-retry policy remain. UI discloses the maximum wait and possible partial failure. An independent offline real-worker test successfully completed an 8.184-second response, proving the longer path is effective without an unbounded wait. It was deployed at 11:16:20 UTC. Server tests passed 139 legacy tests in 5.715 seconds and 214 ApplyPilot tests in 9.338 seconds, all seven changed file hashes matched, and trusted HTTPS health passed. The seven prior records, original verification timestamps and manual “submission result unknown” state were retained. The UI disclosed failure and substituted no demo records. The persisted run lasted **19.034 seconds**, from 11:22:36.910 to 11:22:55.944 UTC, with status failed, found 0 and created 0. ## Remaining limits

Only one additional company is enabled in this checkpoint. Other researched companies are not presented as available or verified. Search is bounded and source-dependent, not full China-market coverage. Public reachability does not grant a broad redistribution license. Live source availability can change. CXMT is experimental and currently blocked in the hosted application. Standalone successful reads do not override the repeated formal-browser failures. Future investigation or a different approved official information source is a separate follow-up, not a promise that this release is operationally complete. There is no scheduled crawler or automatic retry loop.
