# ApplyPilot UI and agent-flow audit

This is the pre-implementation audit, not a claim about final feature completeness. See ../TEST_REPORT.md and ../API_AND_DATA.md for current behavior.

Audit date: 2026-10-09. Read-only source review; no implementation, live requests, or browser execution performed. Backend/test verification is owned separately.

## 1. Baseline and decision

Reviewed the full found `step9.1b/recruitment-system` package and the separate `radar-connector/career-desk-radar` package. Main source policy identifies itself as 9.1b-1 (`radar_policy.json:2`; `RADAR_AGENT_INSTRUCTIONS.md:3`). Connector documentation mentions a later production 9.1c-1, but that does not make this main checkout a verified production 9.1c source. Do not overwrite production from this bundle.

Preserve Python StateAPI, SQLite, CareerAPI, existing application identities and transitions. The current app is already a working persistence/state-machine foundation, not a static-only mock. Its missing product layers are editable confirmed facts, resume import/version/edit review, an application-owned model/runtime, and a complete action-oriented UI.

The immediate safe build can be a synthetic-data-only demo using the same persisted backend and contracts, deployed separately from the private system. Public demo isolation is a release requirement, not a cosmetic mode toggle.

## 3. UI plan: five real workflows

1. **Profile and resume intake.** Import file → extraction draft → edit/correct facts → confirm. Show original source next to uncertain fields; list original and approved resume versions. Confirmed profile revision is visible. Avoid prechecking unknown claims.
2. **Discover jobs.** A server-backed run action and run progress with coverage, counts, errors, imported/duplicate/deferred/rejected. Imported results show official URL, verified time, gate result and source evidence; never describe a signal as a verified job.
3. **Job review.** Requirement/fact evidence alongside fit explanation and risks. Explicit “Add to application queue” rather than ambiguous current “Apply” label. Show that queue approval is separate from final submission. Older pending applications must retain company/match context: current `allRows()` reconstructs rows from the selected-day/queue/attention/history subsets, losing company/recommendation context for older pending rows (`dashboard/app.js:11`; `radar.py:130–133`). Return a complete server-backed job/application projection instead.
4. **Resume tailoring.** Side-by-side before/after with reason/evidence on every proposed edit; accept/reject individual proposals; export an approved, immutable version. No ungrounded one-click “rewrite everything.”
5. **Tracker and attention.** Persistent status, exact resume/profile revision, events, receipts, open questions and next action. Task resolution forms for missing information with explicit reuse scope. P1 adds browser readback and “Review final submission” consent. Unknown outcomes have verification instructions, not a retry button.

A modern UI can replace or modularize the current compressed vanilla `app.js` and CSS. A framework migration is optional, not a prerequisite. All actions must use the live local API against the synthetic demo database; fixtures cannot be the only backing store. Preserve responsive layout, textContent-safe rendering, keyboard focus, accessible dialog, error clearing and request-epoch race protections already present.

Recommended new route families are profile edit/confirm, resume import/version/proposals, agent runs/events, admitted job detail/evidence and task resolution UI. Model boundaries: extract/propose/explain only. Deterministic backend validates schemas, facts, permissions, hard gates and transitions. Untrusted job text is data. Model output never directly performs application transitions or final submission. A no-key mode should return a clear blocked/configuration state; a synthetic deterministic adapter can support tests but must be labelled as test-only.

## 5. Public demo isolation and critical safeguards

- **Never seed the public demo from bundled `candidate-profile.json`.** It contains actual candidate data. Current `db.initialize()` reads this file by default (`db.py:18–20,35–38`); change demo initialization to an explicitly synthetic profile and separate database/artifact directories. Do not publish the original package wholesale.
- Public demo must have its own synthetic dataset, secrets, model/run budgets, origins and deployment. It must not call the production Career Desk, production Radar connector, private Library assets or recruiting submission endpoints. Use non-transmitting browser fixtures for demo actions. Demo reads/writes still persist to its own SQLite database.
- Do not expose legacy raw `/v1/radar/batch` as public or general-agent ingress. All imported “verified” jobs must pass the shared evidence admission contract; owner-only/manual entry is separately labelled.
- Current TEST ONLY fixture can be imported as a live-mode pending application (`radar_recommendations.py:32–40,113–120`), while approval checks only pending status (`state_api.py:230–233`). Its warning text is not a capability barrier. Add an immutable synthetic/test marker and backend prohibition on real transmission/approval for live submission; database-level or service-level enforcement must not depend on the UI hiding buttons.
- Profile and resume edits must not retroactively alter facts used in earlier decisions or submitted applications. Every job score, proposal and application references immutable input versions.
- Never enable real submit merely by flipping the existing `live_submission_enabled` flag. This package has no real adapter, scoped final-consent record or live receipt verifier.
- Keep authorization material out of frontend bundles, reports, source archives and logs. Existing role separation and narrow privacy projection are worth retaining.

## 6. Acceptance and implementation order

**P0-A: persistence and profile/resume contracts.** A synthetic profile can be imported, corrected and confirmed; save/reload/restart preserves exact revision. Reimport creates a new resume version. Concurrent stale edits conflict. Missing facts remain unknown, and original source text remains available for comparison.

**P0-B: app-owned runtime and verified discovery.** Trigger a durable run from UI, process actual allowed official sources with generic search inputs, show source/time/gate/evidence and imported/duplicate/defer outcomes. Closing the UI must not lose run state. Duplicate URL/alias imports preserve original application decision. Model outage/cancellation/restart are explicit. Offline synthetic tests are labelled and do not count as live discovery evidence.

**P0-C: grounded editing and tracker.** Every resume change has before/after/reason/source fact references; unsupported additions are rejected; approving changes creates a new selectable resume version. Queue approval and persisted tracker state survive restart. Task answers resolve through backend. Submitted versus unknown remain distinct, with evidence visible. Public demo can demonstrate these flows only with synthetic data, in isolation.

**P1: browser.** Run real browser tests on local authorized fixtures first: exact fill and DOM readback, changed/duplicate labels, disabled field, page redirect, login/CAPTCHA, disappearing session, repeated resume and state conflict. Closing a task does not bypass a persistent challenge. Add one real site adapter only after scoped authorization and review. Final submission consumes a fresh consent bound to exact versions/form/destination; failed or unknown outcomes cannot automatically resend. Receipt-based success is required.

Shared UI verification: loading/empty/error states, reload, double-click, interrupted fetch, newer navigation, Close/Cancel, Back/Forward and keyboard/mobile layout. Current source has browser contract doubles, not proof of an end-to-end browser pass. Report full-suite and real-browser results separately through the test owner.
